# TindaTrack Database Specification

## 1. Database-Wide Design Decisions

### IDs

TindaTrack will use PostgreSQL auto-generated integer IDs:

```text
INTEGER GENERATED BY DEFAULT AS IDENTITY
```

Conceptually:

```text
id INTEGER PRIMARY KEY
```

with PostgreSQL generating the value.

### Why integer IDs instead of UUIDs?

TindaTrack is:

- a single-store application;
- backed by one PostgreSQL database;
- not a distributed system;
- not generating records independently across multiple databases;
- not required to generate identifiers offline.

UUIDs therefore do not currently solve a domain problem.

Integer IDs provide:

- smaller indexes;
- simpler debugging;
- easier-to-read URLs and logs;
- straightforward Prisma and JavaScript/TypeScript handling;
- more than enough capacity for the expected application size.

`BIGINT` is also unnecessary for the MVP. PostgreSQL `INTEGER` supports over two billion positive values, which is far beyond the expected number of records for a local sari-sari store.

---

# 2. Money Representation

Monetary values will use:

```text
NUMERIC(12,2)
```

This applies to:

```text
Product.selling_price
StockReceiptItem.unit_cost
Sale.total_amount
SaleItem.unit_price
SaleItem.line_total
```

## Why NUMERIC instead of floating point?

Types such as:

```text
REAL
DOUBLE PRECISION
```

store approximate binary floating-point values.

Money needs exact decimal representation.

For example:

```text
₱12.50
```

must remain exactly:

```text
12.50
```

rather than being subject to floating-point rounding behavior.

---

## Why NUMERIC instead of integer centavos?

The alternative would be:

```text
1250 = ₱12.50
```

and storing:

```text
1250
```

as an integer.

That is also a valid design and has excellent arithmetic properties.

For TindaTrack, however, `NUMERIC(12,2)` is preferable because:

- the database value directly represents the business value;
- SQL reports remain easy to understand;
- prices appear naturally as `12.50`;
- PostgreSQL provides exact decimal arithmetic;
- the schema communicates explicitly that these fields represent money;
- this is a useful database modeling decision to demonstrate in the project.

The backend must still avoid careless conversion into JavaScript floating-point values.

When using Prisma, monetary values should be handled using Prisma's decimal representation or another exact decimal strategy rather than relying on ordinary JavaScript `number` arithmetic for financial calculations.

---

# 3. Inventory Quantity Representation

The MVP will support **whole units only**.

Examples:

```text
1 bottle
3 sachets
12 cans
24 packs
```

The MVP will not currently support fractional quantities such as:

```text
0.5 kg
1.25 liters
```

Therefore inventory quantities use:

```text
INTEGER
```

This applies to:

```text
Product.reorder_level
StockReceiptItem.quantity
SaleItem.quantity
StockAdjustment.quantity_delta
StockMovement.quantity_delta
```

This matches the current sari-sari store scope, where products are primarily tracked as discrete units.

If future requirements include products sold by weight or volume, quantity representation can deliberately be migrated to an exact decimal type.

---

# 4. String Strategy

TindaTrack will generally use PostgreSQL:

```text
TEXT
```

for strings rather than automatically assigning `VARCHAR(255)` everywhere.

In PostgreSQL, `TEXT` and unconstrained `VARCHAR` have effectively the same practical storage behavior for this project.

Where a maximum length represents a real application rule, a length constraint can be applied explicitly.

Examples:

```text
sku
email
name
reference_no
reason
```

should have reasonable validation limits.

Fields such as:

```text
contact_details
metadata
```

do not benefit from an arbitrary 255-character database limit.

# 5. Enumerated Values

The following fields have genuinely closed sets.

## User.role

Allowed values:

```text
OWNER

```

Suggested PostgreSQL enum:

```text
user_role
```

---

## Sale.payment_method

Allowed MVP values:

```text
CASH

```

Suggested PostgreSQL enum:

```text
payment_method
```

These values describe how the customer paid.

TindaTrack does not process GCash or Maya payments itself.

## StockMovement.type

Allowed values:

```text
RECEIPT
SALE
ADJUSTMENT_IN
ADJUSTMENT_OUT
```

Suggested PostgreSQL enum:

```text
stock_movement_type
```

Fields such as:

```text
Product.category
StockAdjustment.reason
AuditLog.action

```

should not become PostgreSQL enums yet.

Their possible values may reasonably evolve as the system develops.

# 6. Timestamp Strategy

PostgreSQL timestamps should use:

```text
TIMESTAMPTZ
```

rather than timestamps without timezone information.

Application-generated timestamps should generally default to:

```text
CURRENT_TIMESTAMP
```

Master-data entities that can legitimately change receive both:

```text
created_at
updated_at
```

These include:

- User
- Product
- Supplier

Immutable historical transaction or ledger entities generally do **not** receive `updated_at`.

These include:

- Sale
- SaleItem
- StockReceiptItem
- StockAdjustment
- StockMovement
- AuditLog

A StockMovement having `updated_at`, for example, would imply that ledger evidence is expected to change after creation, which conflicts with its intended semantics.

# User

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `name` | TEXT | No | Non-empty, reasonable length | — |
| `email` | TEXT | No | Unique, normalized lowercase, valid email format handled at API | — |
| `password_hash` | TEXT | No | Non-empty | — |
| `role` | `user_role` | No | `OWNER` or `STAFF` | — |
| `active` | BOOLEAN | No | — | `TRUE` |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |
| `updated_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Additional Rules

Email uniqueness must be enforced by the database.

The API should normalize email addresses to lowercase before storage so that:

```text
Owner@Example.com
owner@example.com
```

cannot become separate accounts merely because of case.

Passwords are never stored directly. Only the resulting secure password hash is persisted.

---

# Product

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `sku` | TEXT | No | Unique, non-empty | — |
| `name` | TEXT | No | Non-empty | — |
| `category` | TEXT | Yes | If present, non-empty | `NULL` |
| `selling_price` | NUMERIC(12,2) | No | Must be `> 0` | — |
| `reorder_level` | INTEGER | No | Must be `>= 0` | `0` |
| `active` | BOOLEAN | No | — | `TRUE` |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |
| `updated_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Low-Stock Rule

Current stock is derived from StockMovement:

```text
current_stock =
SUM(StockMovement.quantity_delta)
```

A Product is considered low stock when:

```text
current_stock <= reorder_level
```

`reorder_level` itself must always satisfy:

```text
reorder_level >= 0
```

Products with historical transactions should be deactivated rather than physically deleted.

---

# Supplier

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `name` | TEXT | No | Non-empty | — |
| `contact_details` | TEXT | Yes | — | `NULL` |
| `active` | BOOLEAN | No | — | `TRUE` |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |
| `updated_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Nullability Decision

`contact_details` may legitimately be absent.

For example, a store may know a Supplier only by name or interact with the supplier personally without maintaining formal contact information.

Therefore:

```text
contact_details = NULL
```

is a valid domain state.

Supplier names should not be globally unique because two distinct suppliers may legitimately have the same or similar names.

---

# StockReceipt

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `supplier_id` | INTEGER | No | FK → `Supplier.id`, `ON DELETE RESTRICT` | — |
| `reference_no` | TEXT | Yes | If present, non-empty | `NULL` |
| `received_by` | INTEGER | No | FK → `User.id`, `ON DELETE RESTRICT` | — |
| `received_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Nullability Decision

`reference_no` may be absent.

A local supplier delivery may not always provide an invoice number, delivery receipt number, or formal external reference.

Therefore the application must support:

```text
reference_no = NULL
```

rather than inventing meaningless reference values.

`received_by` may never be null because inventory receipt activity must always remain attributable to a User.

---

# StockReceiptItem

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `receipt_id` | INTEGER | No | FK → `StockReceipt.id`, `ON DELETE RESTRICT` | — |
| `product_id` | INTEGER | No | FK → `Product.id`, `ON DELETE RESTRICT` | — |
| `quantity` | INTEGER | No | Must be `> 0` | — |
| `unit_cost` | NUMERIC(12,2) | No | Must be `>= 0` | — |

## Unique Constraint

The following pair must be unique:

```text
(receipt_id, product_id)
```

This ensures that one Product cannot appear twice within the same StockReceipt.

For example, this must be rejected:

```text
Receipt #15

Coke × 10
Piattos × 5
Coke × 4
```

rather than automatically combining the duplicate Product rows.

---

# Sale

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `recorded_by` | INTEGER | No | FK → `User.id`, `ON DELETE RESTRICT` | — |
| `total_amount` | NUMERIC(12,2) | No | Must be `> 0` | — |
| `payment_method` | `payment_method` | No | `CASH`, `GCASH`, or `MAYA` | — |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Nullability Decision

`recorded_by` may never be null.

Every completed Sale must remain attributable to the User who processed it.

The `total_amount` value is stored for historical reporting, but it must be calculated by the server.

The client is never authoritative for the total.

---

# SaleItem

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `sale_id` | INTEGER | No | FK → `Sale.id`, `ON DELETE RESTRICT` | — |
| `product_id` | INTEGER | No | FK → `Product.id`, `ON DELETE RESTRICT` | — |
| `quantity` | INTEGER | No | Must be `> 0` | — |
| `unit_price` | NUMERIC(12,2) | No | Must be `> 0` | — |
| `line_total` | NUMERIC(12,2) | No | Must be `> 0`; must equal quantity × unit price | — |

## Unique Constraint

The following pair must be unique:

```text
(sale_id, product_id)
```

This prevents duplicate Products within one Sale.

For example:

```text
Coke × 2
Coke × 3
```

must be rejected rather than silently converted into:

```text
Coke × 5
```

The client should submit a correctly structured Sale.

---

# StockAdjustment

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `product_id` | INTEGER | No | FK → `Product.id`, `ON DELETE RESTRICT` | — |
| `quantity_delta` | INTEGER | No | Must not equal `0` | — |
| `reason` | TEXT | No | Non-empty | — |
| `adjusted_by` | INTEGER | No | FK → `User.id`, `ON DELETE RESTRICT` | — |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Quantity Semantics

Positive values increase inventory:

```text
+5
```

Negative values decrease inventory:

```text
-3
```

Zero is invalid:

```text
0
```

because it would not represent an actual inventory adjustment.

A negative adjustment must not cause the Product's current stock to fall below zero.

That rule depends on existing inventory and therefore belongs primarily in service/transaction logic rather than a simple row-level database CHECK constraint.

---

# StockMovement

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `product_id` | INTEGER | No | FK → `Product.id`, `ON DELETE RESTRICT` | — |
| `type` | `stock_movement_type` | No | Valid movement type | — |
| `quantity_delta` | INTEGER | No | Must not equal `0` | — |
| `sale_id` | INTEGER | Yes | FK → `Sale.id`, `ON DELETE RESTRICT` | `NULL` |
| `stock_receipt_id` | INTEGER | Yes | FK → `StockReceipt.id`, `ON DELETE RESTRICT` | `NULL` |
| `stock_adjustment_id` | INTEGER | Yes | FK → `StockAdjustment.id`, `ON DELETE RESTRICT`, unique when non-null | `NULL` |
| `actor_id` | INTEGER | No | FK → `User.id`, `ON DELETE RESTRICT` | — |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Exactly-One-Source Constraint

Every StockMovement must reference exactly one source transaction.

Exactly one of:

```text
sale_id
stock_receipt_id
stock_adjustment_id
```

must be non-null.

Valid:

```text
sale_id             = 18
stock_receipt_id    = NULL
stock_adjustment_id = NULL
```

Valid:

```text
sale_id             = NULL
stock_receipt_id    = 9
stock_adjustment_id = NULL
```

Valid:

```text
sale_id             = NULL
stock_receipt_id    = NULL
stock_adjustment_id = 4
```

Invalid:

```text
sale_id             = NULL
stock_receipt_id    = NULL
stock_adjustment_id = NULL
```

Invalid:

```text
sale_id             = 18
stock_receipt_id    = 9
stock_adjustment_id = NULL
```

---

## Adjustment 1:1 Constraint

`stock_adjustment_id` must be unique.

This enforces:

```text
StockAdjustment 1 ───── 1 StockMovement
```

rather than accidentally permitting:

```text
StockAdjustment 1 ───── N StockMovement
```

---

## Movement Type Consistency

The database should also enforce, where practical:

### Receipt

```text
type = RECEIPT
quantity_delta > 0
stock_receipt_id IS NOT NULL
```

### Sale

```text
type = SALE
quantity_delta < 0
sale_id IS NOT NULL
```

### Positive adjustment

```text
type = ADJUSTMENT_IN
quantity_delta > 0
stock_adjustment_id IS NOT NULL
```

### Negative adjustment

```text
type = ADJUSTMENT_OUT
quantity_delta < 0
stock_adjustment_id IS NOT NULL
```

This prevents contradictory ledger records such as:

```text
type = SALE
quantity_delta = +5
```

---

# AuditLog

| Column | Type | Nullable | Constraints | Default |
|---|---|---:|---|---|
| `id` | INTEGER | No | Primary key, identity | Auto-generated |
| `actor_id` | INTEGER | No | FK → `User.id`, `ON DELETE RESTRICT` | — |
| `action` | TEXT | No | Non-empty | — |
| `entity_type` | TEXT | Yes | Must accompany `entity_id` when entity-specific | `NULL` |
| `entity_id` | INTEGER | Yes | Logical entity identifier | `NULL` |
| `metadata` | JSONB | Yes | Must not contain secrets | `NULL` |
| `created_at` | TIMESTAMPTZ | No | — | Current timestamp |

## Nullability Decisions

`entity_id` may legitimately be absent.

Some audit activity may describe an action that does not correspond to one specific persisted domain entity.

For entity-specific actions:

```text
entity_type
entity_id
```

should both exist.

For non-entity-specific actions:

```text
entity_type = NULL
entity_id   = NULL
```

The database can enforce that these two fields are either both present or both absent.

---

## Metadata

`metadata` is nullable because not every audit entry requires additional context.

When needed, `JSONB` allows structured details such as:

```json
{
  "changedFields": ["selling_price"],
  "previousValue": "12.00",
  "newValue": "13.00"
}
```

Metadata must never contain:

- passwords;
- password hashes where unnecessary;
- access tokens;
- refresh tokens;
- session secrets.

---

# Delete Behavior

Historical transaction evidence must not disappear because a parent record was deleted.

Therefore the default strategy for TindaTrack's historical foreign keys is:

```text
ON DELETE RESTRICT
```

rather than:

```text
ON DELETE CASCADE
```

---

## User Foreign Keys

```text
Sale.recorded_by
StockReceipt.received_by
StockAdjustment.adjusted_by
StockMovement.actor_id
AuditLog.actor_id
```

Delete action:

```text
RESTRICT
```

A User with history should be deactivated rather than deleted.

---

## Product Foreign Keys

```text
SaleItem.product_id
StockReceiptItem.product_id
StockAdjustment.product_id
StockMovement.product_id
```

Delete action:

```text
RESTRICT
```

A Product with history must be deactivated instead.

---

## Supplier → StockReceipt

```text
StockReceipt.supplier_id
```

Delete action:

```text
RESTRICT
```

Historical receiving evidence must retain its Supplier relationship.

The Supplier should be deactivated instead of deleted.

---

## Sale → SaleItem

```text
SaleItem.sale_id
```

Delete action:

```text
RESTRICT
```

Completed Sales should not normally be deleted.

Using `CASCADE` here would make it easier to accidentally erase historical SaleItems.

---

## Sale → StockMovement

```text
StockMovement.sale_id
```

Delete action:

```text
RESTRICT
```

Deleting a Sale must never automatically remove inventory ledger evidence.

---

## StockReceipt → StockReceiptItem

```text
StockReceiptItem.receipt_id
```

Delete action:

```text
RESTRICT
```

---

## StockReceipt → StockMovement

```text
StockMovement.stock_receipt_id
```

Delete action:

```text
RESTRICT
```

---

## StockAdjustment → StockMovement

```text
StockMovement.stock_adjustment_id
```

Delete action:

```text
RESTRICT
```

The adjustment and its movement are historical evidence and should remain together.

---

The database should enforce simple invariants that depend only on the row being written.

## Product

```text

```

```text
reorder_level >= 0
```

---

## StockReceiptItem

```text
quantity > 0
```

```text
unit_cost >= 0
```

---

## Sale

```text
total_amount > 0
```

---

## SaleItem

```text
quantity > 0
```

```text
unit_price > 0
```

```text
line_total > 0
```

```text
line_total = quantity × unit_price
```

---

## StockAdjustment

```text
quantity_delta <> 0
```

---

```text
quantity_delta <> 0
```

## AuditLog

Either:

```text
entity_type IS NULL
entity_id IS NULL
```

or:

```text
entity_type IS NOT NULL
entity_id IS NOT NULL
```

The database should reject a partially populated entity reference.

# Indexing Plan

Indexes should exist because an actual application query benefits from them—not simply because the table contains the column.

Primary keys and unique constraints already create indexes and should not be duplicated unnecessarily.

---

## 1. Product SKU

Already supplied by:

```text
UNIQUE(sku)
```

### Access Pattern

```text
Find Product by exact SKU
```

For example:

```text
GET product where sku = ?
```

No additional SKU index is necessary because the unique constraint already provides one.

---

# 2. Product Name

Suggested:

```text
INDEX on lower(name)
```

### Access Pattern

Supports Product listing and case-insensitive name-oriented lookup or prefix search.

Examples:

```text
search products beginning with "coke"
sort/filter product catalog
```

For simple MVP searching, this is sufficient as the initial strategy.

If later measurements show that arbitrary:

```text
ILIKE '%coke%'
```

searches are too slow, PostgreSQL trigram indexing can be evaluated then.

It should not be added merely in anticipation of a performance problem that has not been observed.

---

# 3. StockMovement by Product and Time

Suggested composite index:

```text
(product_id, created_at DESC)
```

### Access Pattern

Supports:

```text
view movement history for Product
ordered newest first
```

For example:

```text
WHERE product_id = ?
ORDER BY created_at DESC
```

It also assists inventory-history queries grouped around a Product.

This is one of the project's explicitly expected access paths.

---

# 4. Sales by Date

Suggested:

```text
(created_at DESC)
```

### Access Pattern

Supports:

```text
today's Sales
daily sales reports
sales between two dates
recent sales
```

For example:

```text
WHERE created_at >= start
  AND created_at < end
ORDER BY created_at DESC
```

---

# 5. Sale Items by Sale

The unique constraint:

```text
UNIQUE(sale_id, product_id)
```

already produces an index whose leading column is:

```text
sale_id
```

### Access Pattern

Supports:

```text
load all items for one Sale
```

Therefore a separate:

```text
INDEX(sale_id)
```

would normally be redundant.

---

# 6. Stock Receipt Items by Receipt

Likewise:

```text
UNIQUE(receipt_id, product_id)
```

creates an index beginning with:

```text
receipt_id
```

### Access Pattern

Supports:

```text
load all items belonging to one StockReceipt
```

A separate receipt-only index is therefore unnecessary initially.

---

# 7. StockMovement by Sale

Suggested:

```text
INDEX(sale_id)
```

### Access Pattern

Supports:

```text
retrieve the inventory movements created by a Sale
```

This is useful for:

- transaction investigation;
- audit/debugging;
- future reversal workflows.

Because `sale_id` is nullable, only Sale movements contain a value.

---

# 8. StockMovement by StockReceipt

Suggested:

```text
INDEX(stock_receipt_id)
```

### Access Pattern

Supports:

```text
retrieve all inventory movements created by a StockReceipt
```

---

# 9. StockMovement by StockAdjustment

No additional index is required because:

```text
UNIQUE(stock_adjustment_id)
```

already creates the required index.

### Access Pattern

Supports:

```text
find the one StockMovement generated by an adjustment
```

---

# 10. Audit History

Suggested:

```text
INDEX(created_at DESC)
```

### Access Pattern

Supports:

```text
show recent audit activity
```

If the UI later supports entity-specific history heavily, consider:

```text
(entity_type, entity_id, created_at DESC)
```

but add it when that query actually becomes an application access path.

---

# Initial Index Summary

The initial intentional indexes therefore consist of:

```text
User.email                    UNIQUE
Product.sku                   UNIQUE
Product.lower(name)           INDEX

Sale.created_at               INDEX

SaleItem(sale_id, product_id) UNIQUE

StockReceiptItem(
  receipt_id,
  product_id

StockMovement(
  product_id,
  created_at
)                              INDEX

StockMovement.sale_id          INDEX
StockMovement.stock_receipt_id INDEX

AuditLog.created_at            INDEX
```

Additional indexes should be introduced based on measured query behavior rather than speculation.

# Enforcement Layers

Not every business rule belongs in the same layer.

TindaTrack uses three complementary enforcement layers:

1. Database
2. API validation
3. Service/transaction logic

The goal is not to force every rule into PostgreSQL.

The goal is to place each rule where it can be enforced reliably.

---

```text
Database
+
Service logic
```

The unique constraint prevents multiple movements from pointing to one adjustment.

The service ensures a movement is actually created when the adjustment is created.

---

## StockMovement has exactly one source

Exactly one of:

```text
sale_id
stock_receipt_id
stock_adjustment_id
```

must be populated.

Enforcement:

```text
Database CHECK constraint
+
Service logic
```

The database prevents invalid stored states.

The service selects the correct source when creating the movement.

---

# API Validation

API validation handles malformed or obviously invalid input before business logic reaches the database.

Examples include:

```text
email has valid structure
name is not empty
SKU is not empty
selling_price > 0
reorder_level >= 0
quantity > 0
unit_cost >= 0
payment_method is allowed
reason is not empty
quantity_delta != 0
```

The API should also detect duplicate Product IDs within:

```text
Sale items
StockReceipt items
```

and return a clear validation error.

For example:

```text
A product may only appear once in a sale.
```

rather than waiting for a raw PostgreSQL uniqueness violation.

The database constraint still remains because API validation alone is not sufficient protection for persisted invariants.

---

# Service / Transaction Logic

Rules requiring multiple rows, current state, authorization, or transaction coordination belong in service logic.

## Staff cannot manage users

Enforcement:

```text
Authorization / service layer
```

The database cannot determine whether an API request was authorized to perform an operation.

---

## Sale cannot produce negative inventory

Enforcement:

```text
Service logic
+
Database transaction
```

The service must calculate current stock and verify sufficient inventory before completing the Sale.

This cannot be expressed as a simple StockMovement row CHECK because the answer depends on other StockMovement records.

---

## Negative StockAdjustment cannot produce negative inventory

Enforcement:

```text
Service logic
+
Database transaction
```

The same reasoning applies to inventory-decreasing adjustments.

---

## Sale total is server-calculated

Enforcement:

```text
Service logic
```

The service calculates:

```text
line_total =
quantity × authoritative unit_price
```

and then:

```text
sale.total_amount =
SUM(line_total)
```

The client may display an estimated total, but it is never trusted as the authoritative persisted amount.

---

## Product selling price is authoritative

Enforcement:

```text
Service logic
```

When creating a Sale, the server retrieves the Product's selling price.

It must not blindly accept:

```text
unit_price
```

submitted by the client.

The resulting authoritative price is copied into:

```text
SaleItem.unit_price
```

so historical sales preserve the price used at that moment.

---

## Sale + SaleItems + StockMovements are atomic

Enforcement:

```text
Database transaction
+
Service logic
```

Conceptually:

```text
BEGIN

create Sale
create SaleItems
verify inventory
create StockMovements

COMMIT
```

If any step fails:

```text
ROLLBACK
```

There must never be:

```text
Sale exists
but movements are missing
```

or:

```text
stock decreased
but Sale creation failed
```

---

## StockReceipt + Items + Movements are atomic

Enforcement:

```text
Database transaction
+
Service logic
```

Creating:

```text
StockReceipt
StockReceiptItems
positive StockMovements
```

must occur as one transaction.

---

## StockAdjustment + StockMovement are atomic

Enforcement:

```text
Database transaction
+
Service logic
```

Creating a StockAdjustment without its matching StockMovement would violate the domain model.

Both must succeed or both must fail.

# Guiding Principle

The three layers should reinforce one another:

```text
API validation
      │
      ▼
reject bad requests early
      │
      ▼
Service logic
      │
      ▼
enforce business behavior
      │
      ▼
Database
      │
      ▼
protect persisted invariants
```

API validation improves usability.

Service logic implements the business.

The database provides the final integrity boundary.
